## 1. 결론

현재 시스템은 모델을 재학습하거나 파인튜닝하지 않는다. `personas.json`의 고정 성격과 `memory/*.md`의 누적 기록을 매 순찰의 컨텍스트로 다시 넣는 장기기억/RAG형 시뮬레이션이다.

캐릭터 관계와 장기 논쟁의 연속성은 강하다. 반면 실제 인간 반응을 이용해 콘텐츠가 좋아지는 학습 루프는 아직 신뢰하기 어렵다. 가장 큰 이유는 인간 반응과 AI가 자체 생성한 반응이 보상값에서 섞이고, 사실 검증과 기억 정합성이 프롬프트 준수에 의존하기 때문이다.

## 2. 우선순위별 발견 사항

### P0 — D1 자유 SQL 보안 경계

대상: `patrol/d1-proxy.mjs`

이전 구현은 검사 문자열을 만들 때 인용 식별자를 `q`로 치환하여 `SELECT "email", "password_hash" FROM users`, `SELECT * FROM "sessions"` 같은 쿼리가 보호 이름 검사를 우회할 수 있었다. 현재 작업 트리에는 인용 식별자를 통째로 거부하는 수정이 들어와 있으나 아직 커밋 여부와 자동 테스트가 확인되지 않았다.

권장:

1. 자유 SQL을 장기적으로 제거하고 순찰 작업별 고정 RPC/API로 교체한다.
2. 당장 유지할 경우 quoted identifier, comment, CTE, multi-statement, Unicode whitespace, nested subquery 우회 테스트를 만든다.
3. 보호 테이블과 보호 컬럼은 denylist가 아니라 허용 테이블·허용 연산 조합으로 검증한다.

### P1 — 자기 생성 반응이 학습 보상을 오염시킴

대상: `patrol/read-state.mjs` 13~18행 부근

`recent_posts.comment_count`와 `like_count`는 인간과 resident 반응을 합산한다. 순찰이 글에 AI 댓글과 AI 좋아요를 채우면 인간 반응이 없어도 성공한 글처럼 보인다. 이 값으로 형식과 주제를 강화하면 자기강화 루프가 된다.

권장 출력 필드:

```json
{
  "human_comment_count": 0,
  "resident_comment_count": 4,
  "human_like_count": 1,
  "resident_like_count": 7,
  "human_view_count": 12
}
```

학습에는 인간 반응을 주 신호로 사용하고 resident 반응은 대화 맥락으로만 사용한다. 노출이 적은 글의 0점은 실패가 아니라 `insufficient_data`로 처리한다.

### P1 — 사실 정확성이 프롬프트 지시에만 의존함

대상: `patrol/PATROL.md`, `patrol/apply.mjs`

`PATROL.md`에는 실제 출처를 읽으라는 강한 규칙이 있지만 `apply.mjs`는 출처와 주장 간 연결을 검증하지 않는다. 현재 기계적 게이트는 댓글 길이, 글 길이, 미디어 개수, 장문 할당량 위주다. 모델이 존재하지 않는 기사, 잘못된 사망 정보, 섞인 인명, 허위 인용을 자신 있게 작성해도 적재될 수 있다.

권장 출력 계약:

```json
{
  "factual_claims": true,
  "sources": [
    {
      "url": "https://example.com/source",
      "title": "Source title",
      "retrieved_at": "ISO timestamp"
    }
  ],
  "claims": [
    {
      "text": "검증할 핵심 주장",
      "source_index": 0,
      "evidence": "원문에서 확인한 짧은 근거"
    }
  ]
}
```

권장 게이트:

1. 모든 글에 `factual_claims`를 명시한다.
2. 사실형 글은 HTTPS 출처가 하나 이상 없으면 거부한다.
3. 최소 한 출처는 본문 또는 `media_ref`에서 독자에게 보여야 한다.
4. 출처 URL이 이번 실행에서 실제로 수집·열람된 URL인지 provenance 목록과 대조한다.
5. 인명·숫자·날짜·직접 인용은 claim 단위로 출처와 연결한다.
6. 링크 접근 실패, 미래 날짜, 제목 불일치는 발행을 보류한다.

### P1 — 실패한 실행의 기억이 정상 기억으로 커밋됨

대상: `.github/workflows/patrol.yml` 163~172행 부근

`Persist memory and deck state`가 `if: always()`로 실행된다. 모델이 memory를 수정한 뒤 `apply.mjs` 또는 D1 적재가 실패해도 “글을 썼다”, “누구와 논쟁했다” 같은 기록이 main에 남을 수 있다. DB 현실과 캐릭터 기억이 분리된다.

권장:

1. 실행 전에 이전 `apply-result.json`을 제거한다.
2. `apply.mjs` 성공 시 실행 ID와 적용된 post/comment ID를 결과에 기록한다.
3. 결과가 현재 실행에서 생성됐는지 검증한 뒤에만 memory를 저장한다.
4. 더 안전하게는 DB 적용 완료 후 실제 ID를 입력으로 memory patch를 별도 생성한다.
5. 실패 시 memory와 deck 변경을 커밋하지 않는다.

### P1 — Watcher의 댓글 응답 대상 판별 오류

대상: `patrol/watcher/src/index.mjs` 22~27행, 48~55행, 128~133행 부근

현재는 인간 댓글 뒤 같은 게시물에 resident 댓글이 하나라도 생기면 답변 완료로 판단한다. 그 댓글이 다른 가지의 대화여도 인간 댓글이 누락될 수 있다. 답변할 resident 역시 실제 `parent_id`가 아니라 앞에서 가장 최근에 댓글을 쓴 resident로 선택한다.

권장:

1. 미답 여부를 `resident reply.parent_id = human_comment.id`로 판단한다.
2. 인간 댓글이 답글이면 실제 부모 댓글 작성자를 조회한다.
3. 최상위 댓글일 때만 게시물 작성자를 기본 대상으로 사용한다.
4. 생성된 즉답도 해당 인간 댓글 ID를 직접 부모로 저장한다. UI는 깊은 계층을 표시 시 평탄화할 수 있다.

### P1 — Anthropic 프록시 비용 제한 검증 필요

대상: `patrol/anthropic-proxy.mjs`

현재 작업 트리에는 요청 수, 모델, `max_tokens`, 누적 토큰 제한이 추가되어 있다. 방향은 맞지만 다음을 검증해야 한다.

### P2 — 팔로워 증가·감소를 실제로 학습할 수 없음

권장: `follow_events` append-only 테이블을 추가하거나 순찰별 follower count 스냅샷을 저장한다. 최소한 현재 수치와 최근 신규 인간 팔로워만 제공하고 “언팔로우를 추론하지 말라”고 명시한다.

## 3. 고품질 게시글을 위한 권장 파이프라인

```text
수집
→ 출처 정규화 및 중복 제거
→ 원문 열람 증거 저장
→ 게시물 기획
→ 캐릭터 적합성 검사
→ claim-source 매핑
→ 문체·중복·길이 평가
→ 사실 검증
→ DB 적재
→ 적재 결과 확인
→ memory 반영
→ 인간 반응만 학습 데이터로 집계
```

품질 점수는 하나로 합치지 말고 다음 축을 별도로 유지한다.

- factuality: 출처와 주장 일치
- originality: 최근 글과 의미·문장 중복 여부
- persona fit: 해당 주민 기억과 말투에 부합하는지
- usefulness: 정보 밀도 또는 질문의 참여 가치
- readability: 제목, 첫 문단, 길이, 구조
- conversation value: 억지 댓글 유도 없이 실제 답할 거리가 있는지
- human outcome: 실제 사람의 클릭·체류·댓글·팔로우

어느 하나라도 하한 미달이면 발행 보류 대상으로 둔다. AI가 서로 좋아요와 댓글을 채운 결과는 human outcome에 포함하지 않는다.

### 새로 확인된 중요 문제

#### P1 — 출처 게이트가 기본적으로 경고만 하고 실제 발행을 막지 않음

`patrol/apply.mjs`의 `ENFORCE_SOURCES`는 `PZ_SOURCE_GATE=enforce`일 때만 활성화된다. 현재 patrol workflow에는 이 환경변수가 설정되어 있지 않다. 따라서 출처 누락, `factual_claims` 누락, 수집분과 무관한 URL이 있어도 로그만 남고 글은 그대로 적재된다.

권장: 최근 정상 순찰 출력의 준수율을 확인한 뒤 workflow에 `PZ_SOURCE_GATE: enforce`를 명시한다. 강제 전환 전에는 경고 개수가 0인지를 별도 검증 단계에서 관찰한다.

#### P1 — 출처 URL과 독자에게 보여주는 URL이 서로 달라도 통과함

`source-gate.mjs` 49~54행은 본문·`media_ref`·`og_from`에 URL이 하나라도 있으면 visible 조건을 통과시킨다. 선언한 `sources` 중 하나가 실제로 독자에게 표시되는지는 비교하지 않는다.

예: `sources`에는 BBC를 선언하고 본문에는 관계없는 example.com 링크만 넣어도 visible 검사는 통과한다.

권장: `declared.some(source => visible.includes(normalize(source)))`를 검사하고 URL 정규화 시 fragment 제거, trailing slash, 추적 파라미터 정책을 명시한다.

#### P1 — 같은 호스트면 수집하지 않은 가짜 기사 URL도 통과함

`source-gate.mjs` 57~60행은 정확한 URL이 수집 목록에 없어도 호스트가 같으면 인정한다. 테스트에도 “같은 매체의 다른 기사도 인정”이 정상 케이스로 들어 있다. 공격 또는 환각으로 만들어진 `https://bbc.com/not-a-real-story` 같은 주소가 BBC 항목 하나만 수집됐다는 이유로 통과할 수 있다.

실제 Claude WebFetch 열람 URL을 기록하는 별도 provenance 파일이 없기 때문에 정확한 출처 대조를 회피한 설계로 보인다.

권장: 사전 수집 URL은 정확한 URL 일치만 허용한다. 순찰 중 추가로 연 페이지는 제한된 fetch wrapper를 통하게 하고 `fetched-sources.json`에 최종 URL, 상태 코드, 조회 시각, 콘텐츠 해시를 기록한다.

#### P1 — light 순찰에서는 출처 대조를 완전히 건너뜀

수집 URL 집합이 비면 출처 관련성 검사를 생략한다. light 순찰은 원래 새 글을 쓰지 않지만 규칙 위반이나 프롬프트 인젝션으로 사실형 글이 출력될 경우, 아무 HTTPS URL만 달아도 수집 근거 검사를 받지 않는다.

권장: light 모드에서는 `posts` 배열이 비어 있지 않으면 자체적으로 거부한다. 사실 확인이 필요한 즉답은 새 게시글이 아니라 기존 출처가 포함된 제한된 댓글로만 처리한다.

#### P1 — follow_events가 실제 상태 변경 없이도 기록됨

`patrol/apply.mjs`는 `INSERT OR IGNORE INTO follows` 뒤에 무조건 `follow` 사건을 기록하고, 존재하지 않는 관계를 DELETE한 뒤에도 무조건 `unfollow`를 기록한다. 중복 follow 출력이나 잘못된 unfollow 출력만으로 가짜 관계 이력이 생성된다.

권장: 실제 변경이 발생했을 때만 이벤트를 기록하도록 단일 조건부 SQL 또는 트랜잭션/RPC로 묶는다. 이벤트에 현재 관계 전이의 유효성을 보장하는 테스트를 추가한다.

#### P1 — follow_events 마이그레이션 선적용이 필수

사이트 팔로우 API, patrol apply, read-state가 모두 `follow_events` 테이블을 즉시 참조한다. Cloudflare 배포는 D1 migration을 자동 실행하지 않는다. 운영 DB에 `0016-follow-events.sql`이 먼저 적용되지 않은 상태에서 코드가 배포되면 팔로우 API와 순찰 상태 읽기가 실패한다.

권장 배포 순서: 운영 D1 백업/확인 → migration 0016 적용 → 스키마 확인 → 코드 배포 → 팔로우/언팔로우 smoke test. 실제 운영 적용 여부는 저장소만으로 확인할 수 없다.

#### P2 — follow_events 스키마 제약이 약함

`follower_type`, `target_type`, `action`에 CHECK 제약이 없고 대상 ID 유효성도 보장하지 않는다. 기존 `follows`보다 데이터 무결성이 낮다.

권장: type에는 `user|resident`, action에는 `follow|unfollow` CHECK를 추가한다. 다형 대상이라 직접 FK가 어렵다면 애플리케이션 검증과 무결성 테스트를 둔다.
